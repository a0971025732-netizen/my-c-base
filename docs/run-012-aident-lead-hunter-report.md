## ✅ 先講做對的：計費邏輯正確

只有 `completed` 扣費，4 筆 `expired` 一毛沒收。這比 Run 010 的 FlowCredit（扣費回樣板）健康。**計費正確性沒有問題。**

## ❶ 4 筆 `expired` 從未被實際執行

全部 `failureCode = AGENT_MARKET_RUNTIME_TIMEOUT`，關鍵證據是 **`taskRevision = 2`**：真正跑過的兩筆 revision 到 113 / 126（經歷上百次狀態更新），revision 停在 2 的意思是「建立、然後什麼都沒發生，直到逾時」。這不是 agent 算太久，是**派工後從未被排上執行**。

分布證明這不是特定參數踩雷 —— 涵蓋 X / TikTok / 小红书，30分 / 1小时 / 12小时，英美德加。真正的共通點是**時序**：A1 前 2 筆成功、後 2 筆 expired；A3 的 2 筆全 expired。愈排在佇列後面的愈會被餓死。

→ 建議查 task dispatcher 的並發/佇列處理，以及 `expired` 前是否有過任何 dispatch 嘗試。

## ❷ 第 3 筆起靜默無法送出（並發上限無提示）

A3 後 3 筆：7 個必填欄位全部填成功、`Try free` 未 disabled、無表單驗證錯誤、click 與 force-click 都做了 —— **就是不發 POST**。A3 前 2 筆送得出去，排除帳號與填表問題。幾乎確定是**並發任務上限**，但介面不給任何提示。

真人在這裡會反覆點按鈕，以為自己沒按到。應該 disable 按鈕並說明「你有任務正在進行」。

## ❸ `completed` + 0 條線索 + 收費

2 筆成功執行的報告內容：

> 线索猎手研究报告　本次已保存 0 条线索，报告收录 0 条。已达到本次任务的时长上限，搜索已停止。本次未保存符合条件的线索。

`state=completed`、`failureCode=null`、照常扣費。賣家的 serviceBoundary 有寫「Lead quantity is not guaranteed」，所以**合約上站得住**，這是價值問題而非帳務 bug。但系統兩端都認定交易正常完成，不會觸發任何退款或爭議訊號 —— 使用者只能自己發現買到白紙。

## ❹ run 頁上有一個「死的對話框」

run 頁同時存在一個 `Write a message…` textarea 和真正的結構化表單。填進那個 textarea 並送出：**不報錯、不發請求、不扣費，純粹吞掉**。

這是本輪最先踩到的坑（第一版驅動 9/9 空手就是填了它）。像一扇裝了門把、後面砌了磚牆的門：拉得動，永遠進不去，也沒人告訴你走錯了。真人和自動化工具都會先抓到它。

→ task/direct 模式的 run 頁不該保留這個無作用的輸入框。

## ❺ 老問題再現：表單映射

又出現與 TrainFlow 一字不差的訊息：

> Some examples cannot be safely mapped to this input form and are hidden. Complete the published fields; missing parameters are not guessed.

兩個不同賣家的 agent 撞同一句，說明這是**平台側表單映射的共通缺陷**，不是個別賣家設定失誤。後果是官方範例無法一鍵試用，而這正是新用戶最可能走的路徑。

## ❻ 產品設計疑點：「互动时效」最長 12 小时

必填下拉的全部選項：5分钟内 / 10分钟内 / 30分钟内 / 1小时内 / 6小时内 / 12小时内。

一個找 B2B 採購線索的 agent，最寬只能撈 12 小時內的社媒互動 —— 採購意圖的週期以週計。這不是 bug，但會系統性地讓付費用戶拿到空報告。

**注意：本輪無法證明這是 0 交付的原因。** 唯一用了 12 小时内的那筆（#5）`expired` 了，沒有可比較的結果。窗口窄仍是疑點，但執行層的 ❶❷ 才是已證實的失效原因。
